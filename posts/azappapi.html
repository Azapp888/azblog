AzappApi:一个服务端骨架,顺手长出了 AI 网关

我做过好几个小项目,每次开头都要重新搭一遍同样的东西:跨域、请求日志、统一错误处理、JWT 鉴权、健康检查。前几次还忍着写,写到第 N 次就烦了。于是我把这些"每次都要有、但跟业务无关"的部分抽出来,做成一个开箱即用的 Express 骨架,叫 AzappApi。加新模块的时候,只要往里塞业务路由就行。

骨架里到底装了什么

  • 统一响应结构:成功 { success: true, ... },失败 { success: false, message }。
  • 统一错误处理:代码里抛错就会被兜住,自动返回 JSON 并带上对应的 HTTP 状态码。
  • 请求日志:方法、路径、状态码、耗时,一行一条。
  • CORS:由 CORS_ORIGINS 控制允许的前端来源。
  • JWT 鉴权中间件:标准 Authorization: Bearer <token> 写法。
  • 健康检查:/api/health 返回运行状态与 uptime。
  • 配置集中管理:所有环境变量统一在 src/config.js 读取。
curl http://localhost:8100/api/health
# {"success":true,"status":"ok","uptime":3,"time":"..."}

加一个新模块也极简单:在 src/routes/ 下新建一个导出了 Router 的文件,在 routes/index.js 里 use 一下,需要登录的接口挂上 auth 中间件,访问路径就是 /api/xxx。

结果顺手长出了 AI 网关

骨架搭好之后,我想起自己手上有 DeepSeek、阿里云百炼、豆包(火山方舟)几家不同的模型 Key。平时写小工具,每换一家就要改一次请求地址和字段写法,很碎。既然已经有现成的服务端,我就顺手在里面加了一层 OpenAI 兼容的 AI 聚合网关:对外只暴露 /v1/chat/completions 和 /v1/models,按请求里的 model 路由转发到不同的上游。

这样任何支持 OpenAI SDK 的工具,只要把 base_url 换成本服务地址、api_key 换成统一接入密钥,就能用,完全不用关心背后是谁。

网关的几件正事

  • 统一密钥:所有用户共用一个全局接入密钥,默认 azapp888,可用 GATEWAY_API_KEY 改。
  • 限流与用量:带 RPM / 并发 / TPM / 日额度限制,并统计用量(按模型、按天)。
  • 模型不写死:model_mappings 就是白名单,在后台随时增删启停,没配置的模型直接返回 404。
  • 后台向导:第一次登录管理后台,按"填上游 Key → 加模型 → 复制统一密钥"三步走。系统不预置任何模型。
curl -s http://localhost:8100/v1/chat/completions \
  -H "Authorization: Bearer azapp888" -H "Content-Type: application/json" \
  -d '{"model":"deepseek-chat","messages":[{"role":"user","content":"你好"}]}'

在一台小机器上也能跑

我把它设计成能"单机零依赖"跑起来:默认用 SQLite(靠 Node 22 内置的 node:sqlite)+ 内存限流 + mock 上游,不需要 Postgres、Redis,也不需要先把上游 Key 配好就能起服务看界面。真正上线时,需要一个独立数据库或多实例,再换成 Postgres + Redis + Docker compose 的完整方案。我甚至在一台 RK3566(Debian ARM64、4GB 内存、8GB eMMC)的小机器上跑过它的单机模式。

关于安全

仓库里不含任何真实密钥,.env 已进 .gitignore,只留一份 .env.example 模板。上游密钥在数据库里是加密存的,部署前要自己生成强随机的 JWT_SECRET 并收紧跨域来源。网关这种"所有人都走一个入口"的东西,密钥和限流一定要严肃对待。
